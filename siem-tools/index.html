01/25 SIEM Fundamentals

What is a SIEM?

Security Information and Event Management: one place that collects logs from everything, makes them searchable, and raises alerts when activity looks malicious.

collect → normalize → correlate → alert → retain

Collectpull logs from servers, endpoints, network devices and cloud
Normalizeturn many formats into common field names
Correlatelink related events across sources and time
Alertnotify analysts when a rule matches
Retainkeep history for investigations and compliance
SOC tip

Without a SIEM an analyst must log into every machine one by one. With it, one query covers the whole estate.

analyst@soc:~$
# the slow way: one server at a time
analyst@soc:~$ ssh web01 "grep -c 'Failed password' /var/log/auth.log"
37
analyst@soc:~$ ssh db01 "grep -c 'Failed password' /var/log/auth.log"
3
# ...and 200 more servers. In a SIEM it is one search:
analyst@soc:~$ siem-search 'event.outcome:failure' --last 24h --by host.name
host.name count
web01 37
vpn01 12
db01 3
# (siem-search is a teaching stand-in for any SIEM's search box)
analyst@soc:~$

03/25 SIEM Fundamentals

Parsing & normalization

Every product writes logs differently. The SIEM extracts fields and maps them to a common schema so one query works across all sources.

raw text → fields → common schema → enrichment

Field extractionregex or decoders pull out user, IP, action
SchemasSplunk CIM, Elastic ECS, Sentinel ASIM, OCSF
Timenormalize timestamps to UTC or correlation breaks
Enrichmentadd GeoIP, asset owner, threat-intel matches
SOC tip

If sources call the same thing 'src', 'SourceIP' and 'client_ip', a rule written for one silently misses the others.

04/25 SIEM Fundamentals

Correlation rules

A correlation rule links several events into one meaningful alert, so analysts see incidents instead of noise.

threshold · sequence · first-seen · indicator match

ThresholdN events within T minutes (e.g. 8 failed logins in 2 min)
SequenceA then B (many failures, then a success)
First-seen / raritynew admin account, new country, new process
Indicator matchIP, domain or hash on a threat-intel list
SOC tip

Correlation turns thousands of raw events into the one alert worth a human's time.

analyst@soc:~$
analyst@soc:~$ cat rules/bruteforce_then_success.yml
name: Brute force followed by successful login
severity: high
group_by: [source.ip, user.name]
window: 10m
sequence:
- match: {event.category: authentication, event.outcome: failure}
count: '>= 10'
- match: {event.category: authentication, event.outcome: success}
mitre: [T1110, T1078]
# generic pseudo-rule: every SIEM writes this in its own language
analyst@soc:~$

05/25 SIEM Fundamentals

Alert triage & SOC workflow

Every alert follows the same path. Good notes at each step make the next analyst faster.

triage → investigate → contain → close

Triagereal or noise? how severe? which asset?
Investigatescope it: which hosts, users, time range
Containblock IP, disable account, isolate host
Closetrue positive, false positive or benign; document it
SOC tip

A false positive is still useful: tune the rule so it doesn't fire again for the same benign reason.

analyst@soc:~$
analyst@soc:~$ cat cases/case-0142.md
# Case 0142: SSH password guessing on web01
Alert: Wazuh 5763 sshd brute force (level 10)
Source: 192.168.56.23 (lab attacker VM)
Scope: 29 failures, then 1 success for user 'analyst'
Action: IP blocked (firewall-drop), 'analyst' password reset
Verdict: True positive (authorized lab test)
Tuning: none needed

06/25 SIEM Fundamentals

MITRE ATT&CK mapping

ATT&CK is a public catalogue of attacker techniques. Tagging rules with technique IDs shows what you detect and where the gaps are.

tactic (why) → technique (how) → your detection

T1110Brute Force
T1078Valid Accounts
T1059Command and Scripting Interpreter
T1136Create Account
T1053Scheduled Task/Job
SOC tip

Build an ATT&CK coverage map from your rule tags; uncovered techniques become your detection backlog.

analyst@soc:~$
analyst@soc:~$ grep -H 'attack.t' rules/*.yml
rules/ssh_bruteforce.yml: - attack.t1110
rules/new_local_admin.yml: - attack.t1136
rules/cron_modified.yml: - attack.t1053
analyst@soc:~$ grep -h 'attack.t' rules/*.yml | sort | uniq -c

Splunk overview

A commercial data platform widely used as a SIEM. Data is indexed on arrival and searched with SPL, the Search Processing Language.

forwarder → indexer → search head

Universal Forwarderlightweight agent that ships logs
Indexerparses, indexes and stores events
Search headweb UI and search engine
Ports8000 web · 8089 management · 9997 forwarder input (by convention)
Enterprise Securitypremium SIEM app: correlation searches, risk-based alerting

08/25 Splunk

Universal Forwarder

Installed on each source host, the forwarder watches files and sends new lines to the indexer.

splunk add forward-server · splunk add monitor

add forward-serverwhere to send data (indexer:9997)
add monitorwhich file or folder to watch
-indexdestination index (create it on the indexer first)
-sourcetypetells Splunk how to parse it
outputs.conf / inputs.confthe config files these commands write
SOC tip

Use a dedicated index per data type (linux, wineventlog, web) so searches and retention stay manageable.

analyst@web01:~$
# on web01
analyst@web01:~$ sudo /opt/splunkforwarder/bin/splunk add forward-server 192.168.56.20:9997
Added forwarding to: 192.168.56.20:9997.

15/25 Wazuh

Decoders & rules

Decoders extract fields from a log line; rules match those fields and assign an ID and a level from 0 to 15. The deepest matching rule wins.

/var/ossec/bin/wazuh-logtest

5760sshd: authentication failed ('Failed password', level 5)
5763brute force: 8 × 5760 from one IP in 120 s (level 10)
5710attempt to login using a non-existent user (level 5)
5712brute force: 8 × 5710 in 120 s (level 10)
5715sshd: authentication success (level 3)
SOC tip

Always test a new log format with wazuh-logtest before relying on it in production.

16/25 Wazuh

Custom rules

Add your own detections in local_rules.xml. They build on built-in rules and survive upgrades.

/var/ossec/etc/rules/local_rules.xml

iduse 100000–120000 for custom rules
level0 (ignore) to 15 (critical)
if_sidonly evaluate when a parent rule fired
frequency / timeframethreshold correlation
mitretag with an ATT&CK technique
SOC tip

This rule escalates a successful SSH login (5715) from outside the lab subnet to level 12.

analyst@wazuh:~$
analyst@wazuh:~$ sudo cat /var/ossec/etc/rules/local_rules.xml

<rule id="100100" level="12">
<if_sid>5715</if_sid>
<srcip>!192.168.56.0/24</srcip>
<description>SSH login from outside the lab subnet</description>
<mitre><id>T1078</id></mitre>
</rule>
</group>

File Integrity Monitoring

Syscheck hashes watched files and alerts when they are added, changed or deleted. By default it scans every 12 hours (43200 s).

<syscheck><directories …>

553File deleted. (level 7)
554File added to the system. (level 5)

18/25 Wazuh

Active response

Wazuh can run a script automatically when a rule fires, for example blocking the source IP for a few minutes.

<active-response> in the manager's ossec.conf

commandfirewall-drop adds the IP to the iptables deny list
locationlocal (the agent that saw it), all, defined-agent
rules_idwhich rules trigger it
timeoutseconds before the action is undone
white_listIPs never to block (your admin IP!)
